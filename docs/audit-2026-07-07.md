# ExpertMachina — Principal-Level Repository Audit (2026-07-07)

> Produced by an evidence-based four-phase audit (discovery → audit → strategy → task plan).
> Every finding cites files read directly. Severity: **Critical / High / Medium / Low**.
> (F) = verified fact, (J) = judgment.

---

## 1. Executive Summary

**Overall health grade: B (solid, with one real security defect and systemic operational gaps).**
ExpertMachina is an unusually disciplined, thoughtfully-architected knowledge-governance
backend — clean `routes → crud → database` layering, a genuinely well-designed
identity/authorization boundary (PBKDF2-600k, constant-time compare, envelope-encrypted
outbound secrets, no hardcoded secrets, no injection surface), and a standout suite of six
*self-proving* architectural guard tests that most production codebases never reach. It is
held back from an A by four things:

1. **A High-severity authorization bug**: the REST query endpoint reads the caller's
   clearance tier from the request body (`backend/app/main.py:1219`), so any authenticated
   read-only user can retrieve `RESTRICTED`/`EXECUTIVE` knowledge by asserting a higher
   tier — a real boundary bypass in a product whose entire value proposition is access
   governance.
2. **The operational envelope lags the craft**: no structured logging (only `print()`),
   no Python lockfile, no linter, no Dockerfile, and a hardcoded SQLite DSN.
3. **CI has silently dropped 18 of 64 test suites** — including trust-scoring,
   verification, pipeline, and lifecycle — because the suite list is hand-maintained YAML.
4. **Schema evolution rides on a hand-rolled additive-only migration engine**
   (`backend/app/database.py:741-821`) with no Alembic, no down-migrations, no drift
   detection.

**Top 3 risks:** the clearance bypass (H-SEC-1), CI coverage erosion (H-TEST-1), the
migration engine as the schema grows (H-ARCH-1).
**Top 3 opportunities:** adopt `pytest` + coverage to make the guard discipline
self-maintaining, add structured logging to match the audit-first product story, and split
`main.py` (1,752 lines / 87 routes) into `APIRouter` modules.

The codebase is calibrated well above prototype quality; these are the gaps between
"excellent craft" and "operationally shippable."

## 2. Repo Map

**Purpose.** A knowledge-governance & compilation platform: ingest enterprise documents →
extract & classify knowledge assets → human/policy governance → semantic verification &
conflict detection → compile portable Expert Packages (`.empkg`) → governed consumption by
AI agents via an MCP gateway, with a projection engine rendering disposable graph/vault
"lenses." Core rule: *no evidence = no answer.*

**Stack.**
- **Backend:** Python 3.11, FastAPI 0.136, SQLAlchemy 2.0 ORM, Pydantic v2, SQLite.
  Optional heavy ML: torch/transformers (NLI verifier), llama-index, qdrant-client.
  MCP 1.27 gateway. `cryptography` (Fernet) for credential custody.
  (`backend/requirements.txt`)
- **Frontend (primary):** Next.js 15 / React 19 / Zustand / Tailwind 4, TypeScript.
  (`frontend/`)
- **Frontend (legacy, dead):** vanilla `index.html` / `app.js` / `style.css` at repo root,
  frozen at MVP-0.2.

**Architecture sketch.**

```
Documents ─▶ ingestion / connectors ─▶ extraction + classification ─▶ crud ─▶ database (SQLite)
                                                          │
        governance (policy, tier2, governance_inbox) ◀────┤
        verification_engine / conflict_engine  ◀──────────┤
        query_engine (Verified Answer) ──▶ MCP gateway (agents, clearance-gated)
        package_builder / consumer ──▶ .empkg ──▶ evaluation ──▶ binding
        projections/{engine, renderers/{graph, vault, vis_network_js}} ─▶ disposable lenses
main.py = 87 routes, require_actor/require_perm authZ spine
```

**Key directories.**

| Path | Description |
|---|---|
| `backend/app/` | 43 modules — the entire domain (identity, crud, engines, projections, connectors) |
| `backend/app/main.py` | 1,752-line FastAPI app: 87 routes + authZ guards |
| `backend/app/projections/` | Renderer-agnostic lens engine + graph/vault renderers + vendored vis-network |
| `backend/app/connectors/` | Source framework + local-folder & SharePoint providers |
| `backend/test_*.py` | 64 hand-rolled `__main__` test scripts (46 in CI) |

| `workbench/` | Runtime skill-contract bundles (customer-ops, compliance) + corpora |
| `docs/` | 20+ design docs incl. `DECISIONS.md`, `roadmap.md`, ~360 skill-contract YAMLs |

**Maturity.** Self-labeled `version="0.1.0"` / "MVP Backend," yet at v1.7 with 31 decision
records (D1–D31) and 6 permanent CI guards. Reality: **advanced single-developer prototype
with production-grade governance design but no production deployment** (SQLite, dev-only
run instructions, no live tenant).

**Surprises.** (1) `backend/.venv` (16,545 files) is on disk but correctly gitignored.
(2) `vis_network_js.py` (2,238 lines) is *not* a god file — it's vendored vis-network 9.1.6
gzip+base64-encoded for air-gap safety, with a documented sha256. (3) Zero
`TODO`/`FIXME`/`HACK` markers in the entire codebase. (4) Two frontends, one dead.

## 3. Audit Report

### Security

> Overall **strong**: no hardcoded secrets, no SQL injection (ORM throughout), no unsafe
> deserialization (no `pickle`/`eval`/`exec`/`yaml.load`/`subprocess`), path-traversal
> defenses on uploads and renderers. One real authZ bug.

- **H-SEC-1 (High, F+J) — Caller-supplied clearance bypasses the access boundary.**
  `execute_query` passes `query_in.access_level` from the request body straight into
  `caller_access_level` (`backend/app/main.py:1219`); `require_perm("assets:read")` checks
  *permission*, not *tier*. `query_engine._access_rank` consumes it verbatim
  (`backend/app/query_engine.py:440-446`). Humans have no server-side clearance field, so
  the body value is the *only* gate. **Consequence:** a `READ_ONLY` user sending
  `{"access_level":"EXECUTIVE"}` retrieves and gets answers over `RESTRICTED`/`EXECUTIVE`
  assets. The MCP gateway does it correctly (`backend/app/mcp_gateway.py:84-87` derives
  clearance from the principal registry) — the REST path is the inconsistent one.
  **Status: FIXED 2026-07-07** (see addendum at end of this document).
- **M-SEC-2 (Medium, F) — No login throttling/lockout.**
  `identity.py:420-445`, endpoint `main.py:160-168` — unbounded online brute-force;
  the 600k-iteration hash also makes each attempt a CPU-DoS lever.
- **M-SEC-3 (Medium, F+J) — CORS trusts `EM_CORS_ORIGINS` with `allow_credentials=True`.**
  `main.py:41-48`. Default is safe (localhost); a loosely-set origin list + credentials
  lets a malicious page drive state-mutating routes. No startup guard rejects wildcard.
  (Mitigated: auth is bearer-header, not cookie.)
- **L-SEC-4 (Low, F) — `access_level` is a free-form string, fail-open.** No enum
  validator (`schemas.py:93,111`); unknown values map to `INTERNAL`
  (`query_engine.py:364-365`). A mistyped `RESTRICTED` silently downgrades to `INTERNAL` —
  fail-*open* classification, compounding H-SEC-1.

### Architecture & design

- **H-ARCH-1 (High, F+J) — Hand-rolled additive-only migration engine.**
  `_ensure_columns()` (`database.py:741-821`) `ALTER TABLE ADD COLUMN`s from a dict on
  every startup, using f-string DDL with `PRAGMA table_info` (`database.py:815,820`).
  No drops/renames/type-changes, no down-migrations, no version stamping, no drift
  detection; the raw PRAGMA is SQLite-only. (The f-string SQL uses hardcoded identifiers —
  not injectable, but structurally fragile.)
- **H-ARCH-2 (High, J) — `main.py` is 1,752 lines / 87 routes**, mixing routing, authZ,
  and embedded domain logic (`get_agent_activity` aggregation `main.py:1266-1312`; helpers
  `_validated_policy_fields:757`, `_asset_transition_permission:1144`,
  `_annotated_relationship:1638`). Mitigating: most handlers are thin and delegate
  correctly. Split into `APIRouter`s.
- **H-ARCH-3 (High, F) — `crud ↔ identity` circular dependency papered over with lazy
  imports.** `crud.py:8` imports `identity` top-level; `identity._audit` lazily imports
  `crud` (`identity.py:264`). ≥18 in-function `from app import …` statements exist to
  break cycles (`crud.py:196,212,248,266,383,408,707`; `tier2.py:94-107`;
  `custody.py:191,362`; …).
- **M-ARCH-4 (Medium, F) — Complexity hotspots** (AST-measured length/branches):
  `binding_lineage.build_lineage` 303 L/33 br (`binding_lineage.py:44`);
  `vault.render_files` 270 L/53 br (`vault.py:114`);
  `runner.run_diagnostic` 259 L/45 br (`workbench/customer_operations/runner.py:290`);
  `engine.compose` 202 L/38 br (`engine.py:103`);
  `ingestion.parse_and_index_document` 157 L/30 br (`ingestion.py:77`).
  Disciplined but past reviewable size.

### Code quality

- **M-CQ-1 (Medium, F) — Two silently-swallowed exceptions in the costliest paths.**
  `evaluation.py:51-52` `except Exception: pass` around `json.loads(asset_ids_json)` — a
  malformed field silently yields an empty knowledge universe for a *live* evaluation run.
  `main.py:1277-1278` `except Exception: continue` drops unparseable audit rows from the
  agent-activity view with no counter.
- **M-CQ-2 (Medium, F) — Repetitive `LookupError/ValueError → HTTPException` mapping**
  ×25 in `main.py` — replaceable by two `@app.exception_handler` registrations.
- **L-CQ-3 (Low, F) — `_iso(dt)` duplicated 4×** (`binding_lineage.py:40`,
  `consumption_inbox.py:63`, `governance_inbox.py:48`, `operations_view.py:28`).
- **L-CQ-4 (Low, F) — Pydantic v1 idioms** (`class Config`) across ~83 models in
  `schemas.py` — breaks at Pydantic v3.
- **L-CQ-5 (Low, F) — Uneven return-type hints** in the service layer (`crud.py` 25/31
  defs lack `->`, `identity.py` 16/29).

### Testing

> **Test *authoring* is excellent; the *harness* around it is the weak point.**

- **H-TEST-1 (High, F) — 18 of 64 suites never run in CI.** The CI suite list is
  hand-maintained YAML (`.github/workflows/ci.yml:33-93`); orphaned suites include core
  logic: `test_compile_gates`, `test_lifecycle`, `test_integrity_access`,
  `test_verification_engine`, `test_trust_score`, `test_validation_engine`,
  `test_pipeline`, `test_retrieval_engine`, `test_generation_engine`,
  `test_package_builder`, `test_audit`, `test_evaluation_framework`,
  `test_claim_verdicts`, `test_nli_verification`, `test_docx`, `test_benchmark_crud`,
  `test_audit_expansion` (+ `test_conflict_engine` deliberately deferred). Some need the
  ~1GB NLI model; **many don't** and are simply orphaned.
- **M-TEST-2 (Medium, F) — Tests are `__main__` scripts, not run under a test runner.**
  No `pytest`/`conftest`/`pyproject`; first failing assertion aborts the whole file;
  adding a suite means editing CI YAML by hand — the mechanism that orphaned the 18.
- **M-TEST-3 (Medium, F) — No coverage measurement anywhere.**
- **M-TEST-4 (Medium, F) — Semantic-conflict engine has no CI guard.**
  `test_conflict_engine.py` needs the ~1GB model; the promised "cached nightly job"
  doesn't exist; in a fresh env the test silently SKIPs.
- **M-TEST-5 (Medium, F) — Zero frontend tests** (only `tsc --noEmit` + `eslint`).
- *Strength:* the six guard suites use AST sweeps to enforce invariants and each **plants
  a violation to prove its own detector fires** (`test_agent_authorship_guard.py:808-855`).
  Tests assert rich behavior, are hermetic (ephemeral SQLite, no network).

### Performance

> Healthy for current scale; no blocking issues.

- **M-PERF-1 (Medium, F) — N+1 in citation building.** `_build_citation` runs 2 queries
  per citation (`query_engine.py:368-370`) inside per-citation loops
  (`query_engine.py:163,190,291`) → 2N queries per answer. Linear cliff at scale.
- **L-PERF-2 (Low, J) — SQLite + `check_same_thread=False` + FastAPI threads**
  (`database.py:8`) serializes writes — a scaling ceiling, not a bug today.

### Dependencies

- **H-DEP-1 (High, F+J) — No Python lockfile.** `requirements.txt` pins exact `==` but no
  hashes and no transitive lock; `torch`/`transformers` drag dozens of unpinned
  transitives. *Asymmetric:* the frontend commits `package-lock.json` and runs `npm ci`.
- **M-DEP-2 (Medium, J) — Heavy ML stack installed unconditionally.**
  torch/transformers/sentencepiece/llama-index install on every CI run even though
  `EM_NLI_VERIFICATION=off` there. Belongs in an optional `requirements-nli.txt`.
- **L-DEP-3 (Low, J) — No `pip-audit`/outdated check.**

### DevEx & operations

- **H-OPS-1 (High, F+J) — No structured logging; `print()` only.** Zero `logging` imports
  in `app/`; 35+ `print()` calls on real error paths (`claims.py:90`, `extraction.py:126`,
  `connectors/framework.py:82`, `evaluation.py:406`,
  `verification_engine.py:56/89/117/147`). The single most surprising gap for an
  audit-first product. (The DB audit ledger is *domain* provenance, not *operational*
  observability.)
- **M-OPS-2 (Medium, F) — No Python linter/formatter in CI.** No
  ruff/flake8/black/isort, no `pyproject`/`.flake8`/`pre-commit`.
- **M-OPS-3 (Medium, F) — No Dockerfile / deployment artifact.** Run instructions are
  dev-only (`README.md:311,319`).
- **M-OPS-4 (Medium, F) — DB DSN hardcoded.** `DATABASE_URL =
  "sqlite:///./expert_machina.db"` with no env override (`database.py:6`).
- **M-OPS-5 (Medium, F+J) — Dead legacy frontend at repo root.**
  `index.html`/`app.js`/`style.css` frozen at MVP-0.2 (2026-06-10), unreferenced by
  README, not served by the backend. Delete or move to `archive/`.

### Documentation

> **Exceptionally strong** narrative docs (README 356 L, DECISIONS 889 L, roadmap 879 L,
> accurate run instructions). One gap: `docs/architecture.md` is only 71 lines — thin for
> a 43-module system; a newcomer has no single structural map. (Low.)

### Strengths to preserve

No hardcoded secrets; PBKDF2-600k + constant-time compare; envelope-encrypted outbound
secrets with fail-closed `EM_SECRET_KEY`; ORM-only (no injection); path-traversal
defenses; clean authN/authZ separation with a code-resident role matrix; centralized
audit writes (2 construction sites); six self-proving AST guard tests; hermetic
behavior-asserting tests; zero TODO/FIXME; no dead code in domain modules; disciplined,
well-commented large functions.

## 4. Improvement Strategy

**Theme 1 — One authorization model, enforced server-side.** (H-SEC-1, L-SEC-4,
M-SEC-2/3.) Target: clearance and access-level derive from the authenticated principal
(as the MCP gateway already does), never from request bodies; classification levels are a
validated enum that fails *closed*; login is throttled; CORS wildcard rejected at startup.
Principle: *the server decides authority; callers propose, never assert.*
Done when: a `READ_ONLY` user cannot retrieve above-tier assets on any path; a regression
test proves it.

**Theme 2 — Make the test discipline self-maintaining.** (H-TEST-1..5, M-TEST-*.)
Target: `pytest` auto-discovers all suites (no hand-listed YAML), coverage measured and
gated on core modules, model-dependent suites in a cached nightly job.
Principle: *CI should discover tests, not enumerate them.*
Done when: `pytest -q` runs everything; core-module coverage tracked.

**Theme 3 — Close the operational envelope to match the craft.** (H-OPS-1, H-DEP-1,
M-OPS-2/3/4, M-DEP-2.) Target: structured `logging` with levels + request id; a Python
lockfile with `pip-audit`; ruff in CI; a Dockerfile; env-configurable DSN; NLI deps as an
optional extra. Principle: *an audit-first product must be observable and reproducible.*

**Theme 4 — Reduce structural risk before the schema/routes grow further.** (H-ARCH-1/2/3,
M-ARCH-4, M-CQ-*.) Target: Alembic; `main.py` split into routers; `crud↔identity` cycle
broken into a lower-level module; shared utils extracted; error→HTTP mapping centralized.
Principle: *pay down the shortcuts that compound with size.*

**Explicit non-goals (recommend NOT doing now).**
(a) Rewriting to Postgres/microservices — SQLite is fine until a real multi-tenant
deployment exists; keep the seam instead.
(b) Deleting the `__main__` test bodies — wrap them in pytest, don't rewrite.
(c) Frontend test framework build-out — low payoff until the UI stabilizes.
(d) Refactoring the disciplined large functions purely for line count.

**"Done" signals.** Zero Critical/High findings open · CI fails on lint + any uncollected
test · core-module coverage ≥80% · `pytest` runs 64/64 suites · no `print()` on error
paths · locked+audited Python build · a clearance-bypass regression test passes.

## 6. Open Questions

1. **Product stage & deployment intent.** Is a real multi-user/multi-tenant deployment on
   the near roadmap? Gates SQLite→Postgres seam, Docker, and login-throttle urgency.
2. **Human clearance model.** RESOLVED & RATIFIED 2026-07-07: clearance derives from role
   (code-resident `identity.ROLE_CLEARANCE`, mirroring the MCP gateway's principal-registry
   derivation) — ADMIN & GOVERNANCE_REVIEWER → EXECUTIVE, KNOWLEDGE_OPERATOR & READ_ONLY →
   INTERNAL, unknown roles fail closed to PUBLIC; a body `access_level` may lower but never
   raise the tier. Future refinement (explicit per-user `Principal.clearance` for humans)
   remains available as an additive change — the role map is the fallback default.
3. **NLI/model story.** Shipping feature (needs cached nightly CI) or experimental
   (gate behind an extra)?
4. **Legacy root frontend.** Confirm `index.html`/`app.js`/`style.css` safe to delete —
   nothing serves or references them, but they may be a separately-deployed demo asset.
5. **Performance targets.** Will the corpus reach thousands of assets? Determines whether
   the N+1 and SQLite concurrency move from Low to High.

## Addendum — H-SEC-1 fix (2026-07-07)

Applied the same session as the audit:

- **Regression test first** (`backend/test_authorization.py` extension): a `READ_ONLY`
  principal requesting `{"access_level": "EXECUTIVE"}` must NOT receive
  `RESTRICTED`/`EXECUTIVE` assets. Written red against the pre-fix code, green after.
- **Fix**: `execute_query` derives the effective clearance from the authenticated
  principal via a code-resident role→clearance map in `identity.py` (mirroring
  `mcp_gateway.agent_clearance`'s registry-derivation principle). The body
  `access_level` is retained for compatibility but is now a *cap-only proposal*:
  `effective = min(requested, principal_clearance)` — it can narrow, never widen.
